# ADR-010 — Sharing a project's code with a specialist: strategy ladder

Status: accepted (owner, 2026-07-17)
Date: 2026-07-17

## Context

With specialists that may execute outside a project's primary session
(ADR-008), the question is not "how do specialists get GitHub access" — the
directive forbids that framing outright. It is: **how does a specialist
inspect, modify, or test code whose source of truth lives in the project's
primary session** (ADR-007), under least privilege?

Fixed constraints (all already normative): repository access belongs to the
project and its session, never the specialist (ADR-006, FR-45/46/47,
SEC-11 — one fine-grained PAT per repo, held in the seam's session config);
role instructions reach a turn via `--append-system-prompt`
(B5-04, spike S-04) — so a specialist can execute *inside* any session
without that session being "theirs"; the substrate has **no cross-session
file access, snapshots, or read-only mounts** (verified at `0cd4ed5`;
workspace = per-session host bind mount, `dockerManager.ts:491-501`), and
file download is owner-only (`routes/sessions.ts:1173-1217`).

## Options

Evaluated per the directive's §17 (A–E), plus do-nothing:

1. **Do nothing** — every specialist gets its own clone + credential.
   Rejected: global credentials, duplicated repos, drift, and lateral access
   — the exact failure the directive names.
2. **A — execute the specialist in the project session.** Proven mechanism
   (B5-04); real state, real credentials, no copies.
3. **B — worktree/branch inside the project session's workspace**, created
   and owned by the project session (`git worktree` over exec — the
   substrate is not involved and needs no new capability).
4. **C — read-only snapshot/artifact** for analysis work.
5. **D — diff + structured report** for review work.
6. **E — transfer artifact** when the specialist cannot execute in the
   project session.
7. **Cross-session read-only mounts** (would need upstream work). Not
   requested: D/E cover current needs; recorded as a possible future ask
   only if evidence demands it.

## Decision

A ladder, selected deterministically by work type (the execution-target
selector records the choice as `workspaceStrategy` on the run, ADR-008):

| Work | Strategy |
| --- | --- |
| Implementation modifying the project | **A**, preferably on **B** (task branch/worktree) — default |
| Functional QA / running tests | same branch/worktree as the implementation, executed from the project session (or a controlled temp environment) |
| Code review | **D** — diff + `ImplementationReport`, read-only |
| Architecture consulting / planning | **C** — read-only snapshot or selected context |
| Work unrelated to any project | the specialist's personal session (ADR-008) |

Rules that hold across all strategies:

- The **project session remains the source of truth** and the only holder of
  repo credentials. PRs are created and updated from it (or by an operation
  delegated *to* it) via its own `gh` credential — never from a specialist's
  session, never with a specialist-held token. No PR merges before human
  approval (ADR-009).
- Worktrees/branches are created, tracked, and cleaned up under orchestrator
  direction, executed by the project session; branch operations serialize
  through the project session's queue (I-2 per workspace). Two sessions never
  modify the same workspace concurrently without an explicit strategy; files
  are never copied informally.
- Artifacts (C/E) are generated by the project session, exclude secrets and
  out-of-scope paths, record what was shared, and expire where appropriate.
- Each step records a **DelegatedWorkspaceAccess**-style entry (task,
  specialist, access mode `read-only | worktree-write |
  project-workspace-write | test-execution`, optional path/command bounds,
  expiry) — revocable, auditable, no lateral reach into other projects.
  Secrets stay under the project session's (or the substrate's) control; a
  specialist can trigger an authorized operation without ever holding the
  secret's value.

Answers the directive's §21 questions concretely: a specialist executes
logically inside an existing session with no new session (proven, S-04);
worktrees are plain git via exec; QA receives exactly the implementer's
version as a committed branch/worktree ref plus the `ImplementationReport`;
work survives specialist failure because it lives in commits; manual owner
intervention is tolerated (runs serialize per workspace; detection via git
state and the substrate's operate audit trail) and there are never two
hidden versions of a project.

## Consequences

- No upstream dependency: every strategy works with exec + the ADR-007
  identity model. (Cross-session mounts explicitly *not* asked of upstream.)
- Cleanup is a real obligation: task terminal states trigger
  orchestrator-ordered worktree/branch/artifact cleanup; leaks are visible in
  the task inspector.
- The `DelegatedWorkspaceAccess` record adds one more snapshot-style audit
  row to the run path — consistent with `capsSnapshot`/`policySnapshot`
  (I-8) rather than a new mechanism.
- Strategy selection logic lives in the deterministic selector (ADR-008),
  keeping models out of authority decisions (SEC-01).
